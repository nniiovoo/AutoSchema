# Polymer-card contract

This additive workflow identifies polymer entities and describes them. It does not call the older application selector or use conductivity, commercial origin, source role, or field completeness as retention criteria.

## Input source document

`{paper_id, title, domains, source_files, chunks}`. Each chunk has `chunk_id`, `text`, `source_part`, `locator`, optional `page`, and `document_sha256`. IDs and source locations are supplied by source preparation, never invented by the model. Domains are discovery metadata, not evidence of polymer identity.

JATS-derived text declares `text_transformations:["jats_script_notation_v1"]` in source/chunk metadata and resolved evidence. Numeric superscripts/subscripts retain Unicode position, such as `10⁵`, `cm⁻¹` and `Li₂`; unsupported script characters retain explicit `^{...}` or `_{...}` boundaries. The XML bytes and their SHA256 are unchanged. Quotes match this declared derived text, not the publisher's typeset appearance. Keep earlier run snapshots intact when comparing extraction versions.

## Model response

`{paper_id, entities: [...]}`. New live requests use strict Structured Outputs through `build_response_format()`, schema name `polymer_cards_strict_v4`. Version 4 changes live evidence to source-span selection; version 3 introduced explicit source-conflict notes. Earlier v2/v3 requests remain historical artifacts. The persisted card contract remains `polymer-cards-v1` for replay compatibility. All declared live keys are required and objects reject extra keys. Nullable fields represent unknown information without inventing it. `extraction_profile()` records the output format, schema name, schema SHA256 and system-prompt SHA256 in live run metadata/traces. A model or Azure deployment without strict JSON-schema support fails explicitly; there is no silent fallback to JSON-only mode. Replay remains compatible with earlier inputs that omit newly added fields.

The current schema reaches ten levels when expanded objects and arrays are counted. Recheck provider compatibility before adding a deeper nested field.

Each live entity has:

- `entity_id`: unique within the paper; `name`: exact source label, preserving spelling/case rather than an invented expansion; `identity_evidence`: evidence references. Other source-supported names belong in aliases. Generic family descriptions must not duplicate exact member cards or absorb chemically different controls.
- `identity_kind`: required since live v2 output; `specific_polymer`, `polymer_family`, or null. A specific polymer can be a purchased precursor or one named formulation. A family is a broad class/series, not another exact member. Null expresses unresolved scope and is required for nonpolymer roots. Legacy replay may omit the field. Exact member identity must have a named original passage; a range-only quote is not automatically expanded into missing labels.
- `classification`: `{is_polymer: true|false|null, reason: string, evidence: [...]}`. Null is unresolved classification. True/false without usable original evidence is not a final retention/discard decision.
- `aliases`: a list of facts; `description` and `role`: a fact or null. Role describes the entity's role in this paper.
- `specimens`: a list of `{specimen_id, label, evidence}` linked to this polymer. A salted specimen is not an alias for its matrix.
- Exactly the six information groups `monomers`, `composition`, `synthesis_text`, `properties`, `applications`, `source_tag`. Each has `{status, items}`; since live v3, `properties` additionally requires `conflicts`, which is empty when no unresolved source discrepancy was identified. Status is `reported`, `not_found_in_provided_text`, `needs_review`, or `conflicting`. Earlier replay inputs may omit optional identity details, specimens or groups; missing groups are filled as not found, without discarding a polymer. Earlier properties groups may omit `conflicts`.

A fact is `{value, evidence, ...}`. Facts in the six groups additionally carry their parent `entity_id`. Value is original source wording or a supported descriptive summary; source text remains in the attached evidence. A new live evidence reference is `{chunk_id, span_id}`, selected from the supplied source catalogue. The model does not return a quotation, source offsets or provenance fields. The validator resolves the chosen ID to the exact original source characters and resolves location metadata from the document chunk. Historical replay may still supply `{chunk_id, quote}` under the unchanged strict containment check. Do not supply freestanding field-wide values and evidence arrays.

Specialized fact fields:

- Monomers: `role` distinguishes monomer, polymeric reactant, chain extender, etc.; null is allowed in live output, and earlier replay may omit it.
- Composition: required live `basis` describes molar feed, mass ratio, concentration, or another reported basis. Unknown basis is null and the fact goes to review; do not guess it. Required live `specimen_id` may be null when no specimen-specific scope is established. Null optional scope is treated as absent in the accepted fact. Keep amounts/ratios and ingredient names together in `value`; a feed molar ratio and a later polymer:salt mass ratio are separate facts.
- Synthesis text: meaningful source-grounded process text is allowed. Required live `specimen_id` may be null, as above; an established specimen link distinguishes polymer synthesis from later film preparation.
- Properties: `property`, original `value`, original `unit` (or null when absent/inapplicable), `specimen_id`, `specimen_evidence` and `conditions` as a list of `{name, value, evidence}`. The live schema permits a null specimen ID or empty specimen evidence to express uncertainty, but these facts are quarantined rather than accepted. Accepted new properties require a linked specimen and nonempty original `specimen_evidence`, including preparation/testing context connecting the result to its exact form. Earlier replay properties may omit the new evidence field. Preserve original numeric notation and bounds/approximation; no automatic conversion is promised. Property values, units and conditions must match the resolved supporting source text; numeric fragment checks reject partial ranges, ratios and exponents while allowing sentence punctuation. Preserve `%` in the original raw value where reported and also supply `%` in `unit`; genuinely dimensionless quantities may keep a null unit.
- Applications: `claim_type` is `demonstrated`, `proposed`, or `unspecified`; it is descriptive, not a suitability gate. Demonstrated claims should cite actual current-paper experiments, not only introductory proposals. Reported component uses, such as cathode binder, also belong here.
- Source tag: `value` is `author_synthesized` or `commercially_purchased`. If not established for that polymer, leave the group empty. Evidence must be reviewed to distinguish purchased precursors from the final product.

## Source-span evidence in live V4

`source_span_catalog` contains `{span_id, chunk_id, start, end, text}` entries generated only from the supplied primary text. IDs bind the catalogue version, paper identity, chunk identity, source/text hashes and exact character range. Each chunk has a full-chunk fallback plus deterministic paragraph/sentence choices. These lexical boundaries are navigation aids, not scientific sentence interpretation. Prefer a narrow span with its subject, select separate Results/Methods spans when needed, and retain multiple spans for a supported connection crossing sentence boundaries.

`resolve_span(document, chunk_id, span_id)` accepts only an ID belonging to that current paper/chunk and retrieves `text[start:end]`. Unknown IDs, cross-paper/chunk selections, changed source ranges or mixed new references that also supply model-written quotations/offsets/provenance go to review. The raw model response remains unchanged. Accepted evidence includes the retrieved `quote`, `span_id`, `source_start`, `source_end`, `evidence_origin:source_span_selection` and `catalog_version:source-spans-v1`, together with the usual source metadata. Offsets are zero-based Python Unicode codepoint offsets with an exclusive end; they are not UTF-8 byte or JavaScript UTF-16 offsets.

When selected V4 spans overlap or are adjacent within the same source chunk, `combine_adjacent_spans` can add exact contiguous support with `evidence_origin:source_span_selection_union`, the original `span_ids`, and the resulting offsets. It rechecks the selected IDs, text, offsets and source metadata, and may bridge whitespace only—never unselected words, punctuation, numbers or chemical signs. The original individual selections remain; no new model-selectable ID is invented. Legacy quote arrays are not joined or repaired. Readable output labels this as derived adjacent-source support. Like an individual selection, a union establishes retrieval provenance, not scientific attribution.

This is retrieval, not fuzzy quotation repair. The program does not normalize `M_{n}` into `Mn`, change `CH₂Cl₂` into `CH2Cl2`, choose a chemically equivalent name, repair a numeric qualifier or fill a missing condition. Legacy `{chunk_id,quote}` references still require original-source containment after the existing NFC/whitespace handling; a failed legacy quotation is not silently converted into a span selection. A valid selected span guarantees its source characters, not the interpretation, polymer classification, sample ownership or completeness of its associated claim. `quote_matched` remains the mechanical evidence label; it does not measure whether a V4 model accurately copied a quotation, because it selected an ID instead.

## Validation and output

`build_cards(document, response)` returns `{paper_id, cards, discarded_entities, review_queue, validation_issues, attribution_warnings, statistics}`. Invalid field facts go to review and do not remove an otherwise retained polymer. Preserve the raw response separately. Identity or classification with invalid/absent evidence goes to the classification review queue. A confirmed nonpolymer is omitted as a standalone card but may remain as an ingredient.

`attribution_warnings` are separate advisory records for shared sample labels across polymer cards or ambiguous neat/additive-containing forms. They appear on readable cards and in nested card/result JSON. They do not add quarantined facts, establish chemical equivalence, merge records or automatically reassign measurements. Counts of warnings and review records therefore describe different checks. The rules are deliberately limited; absence of a warning does not certify sample attribution.

Some source-link failures now quarantine the property itself. `property_sample_evidence_names_alternate_form` means separate sample-link evidence explicitly names a more specific additive-containing form while the chosen specimen is bare; numerical comparison quotes alone do not trigger this check. The check also handles an omitted alternative specimen conservatively, without inventing an ingredient or relinking the result. `family_measurement_requires_specific_polymer` holds a numerical observation placed under an explicit family; `measurement_polymer_scope_unresolved` holds numerical observations with explicitly unresolved live scope. The polymer root remains retained. These guards are source/text checks, not general chemical reasoning or a guarantee that every experiment's conditions are complete.

A narrow cell-stack exception prevents an explicit electrode/membrane/electrode arrangement such as an introduced asymmetric `SS/SHPEM/Li` cell from being read as an additive-containing polymer. The selected membrane must be the bounded central layer, both outer layers must use recognized electrode labels, and nearby source text must explicitly identify a symmetric, asymmetric, electrochemical or blocking cell. This only limits that lexical mismatch signal. Other mixing/preparation text remains checked, including additive forms appearing in the same paragraph. It does not establish a replacement sample link, identify every possible electrode or approve an otherwise unsupported observation.

`property_unit_field_missing_for_explicit_percent` holds a numerical property whose raw value visibly contains a percent sign while its separate `unit` is null. The validator preserves the original proposal in review; it does not silently fill or convert the unit. This deliberately narrow check does not detect every omitted unit. A null unit remains allowed for source-supported dimensionless quantities such as dispersity or a transference number.

Accepted numerical properties receive `conditions_review_status:not_captured` when their condition list is empty, or `captured_not_scientifically_verified` when at least one condition was captured. This is output metadata, not a new model-supplied property key. It describes presence, not completeness, applicability or correctness. Readable cards show empty numerical conditions as uncaptured and direct the reviewer to the Methods/sample context. The model is instructed to search testing Methods and cite attributable protocols separately; preparation/reaction temperatures must not be relabeled as instrument temperatures.

Property conflicts introduced in live v3 have `{property, description, specimen_ids, evidence}`. Each nonempty conflict requires an explanatory text, at least one unique parent-local specimen ID and verbatim source evidence. The prompt asks for both relevant source reports, while the validator checks supplied quotations and links rather than deciding whether the reports concern the same physical specimen. Valid notes survive under `properties.conflicts`, set the group to `conflicting`, and produce an `unresolved_source_property_conflict` validation flag. Their associated observations remain separate even when their sample IDs or condition labels differ. Invalid conflict metadata goes to review without erasing accepted measurements; it does not become a corrected thickness value. The program never averages the reports, chooses one or invents a wet/dry explanation. The selected Chen reference checks that the Methods and Results thickness reports remain explicit and that PE-film thickness is not borrowed for SHP.

Only source identity, type/shape, parent/specimen links and verbatim quote containment are mechanically checked. Use the status `quote_matched`, not scientifically verified. Classification and semantic attribution remain model/reviewer judgments; evaluated examples must report their review provenance. Unknown or contradictory values remain visible.

Paper-scoped IDs prevent cross-paper or cross-sample merging. A scalar value repeated at different temperatures must remain separate observations. Names containing `/`, ratios and units are never split by a generic normalizer. Any statement of experimental reproducibility, extraction accuracy or complete material coverage needs a separate evaluation.

Live runs checkpoint each successfully extracted and validated paper. `run_complete` remains false until all requested papers finish; metadata includes `papers_requested`, `papers_completed`, `model_calls_attempted` and completed `model_calls`. If a later handled request/validation failure occurs, completed papers remain available with `run_complete:false` and `failed_paper_id`; readable output explicitly identifies the partial run. A malformed/truncated response never contributes partial paper records. If the first paper fails there is no new completed-paper checkpoint. Use a fresh output directory for each comparison run. Timeouts and connection failures have safe diagnostic labels without raw provider error text; there are no automatic retries.

## Source-grounded model revision

`--repair-records PRIOR_RAW --repair-sources PRIOR_SOURCES` requests a new model revision, labeled `live_model_revision`. Both flags are required together and are mutually exclusive with replay's `--records`. Prior response IDs must exactly match the manifest, and the saved source chunks, text, hashes, locations and declared transformations must match the current source representation. The CLI protects both prior inputs from output overwrite.

Each paper makes one bounded revision request. It receives all primary chunks and the current span catalogue, previous records as untrusted proposals, compact validator feedback and a case-sensitive exact-name/alias source index with candidate span IDs. New output selects current source-span IDs even when prior proposals used quotations. The index ranks candidate original passages, does not expand label ranges, and is not proof of chemical identity or sample ownership. No checked reference card or evaluation answer file is loaded by this route. The model returns a full new response; it does not edit the prior file or receive an automatic replacement specimen link.

Run metadata records the two prior-file hashes. Each revision trace records `request_mode:source_grounded_model_revision`, the canonical prior-response hash and actual request-prompt hash. A request hash belongs to the source and validator/prompt policy used at that time. Reconstructing with a later feedback policy can differ; retain the historical trace and disclose the difference rather than replacing its hash. Subsequent program revalidation is separate, makes no model call and must record its validator revision and preserve raw model responses.

Checked examples and focused source expectations are evaluation inputs only. Report whether a result matches the value, exact sample, metric meaning, conditions and attached Methods evidence separately. A value can be correct while a complete reference case still needs review for missing protocol metadata; representation differences are not automatically scientific errors. Selected matches are not an overall accuracy score.

The additive evaluation contract accepts `unit_field_required:true` on a selected measurement expectation. When its expected unit is nonnull, embedding the unit in raw `value` no longer satisfies that explicit field requirement; the saved fact must also supply the expected separate unit. Dimensionless reference cases may still expect null. `conflict_expectations` require the linked, source-supported observations as well as a matching explicit conflict note, its relevant source evidence and a `conflicting` properties group. A single thickness observation, a generic note without its sources, or a source mismatch does not pass. Frozen older references are not rewritten to improve a later run's apparent performance.

## Bounded model context review

This library route is separate from fresh extraction and full-record revision. `llm.review_context_document(client, model, document, previous_response, max_output_tokens=16000, review_focus=None, strict_focus=False)` makes a separately recorded model request for context proposals. It receives original source data and an existing model response as untrusted proposals. It does not read checked references. The returned response has `{paper_id, edits}` under strict schema `polymer_context_review_v1`; no new complete extraction is generated.

Each edit names an existing `entity_id` and original zero-based `property_index`, with an `anchor_sha256` binding the entity/index, property label, original value and unit. It may replace only `specimen_id`, `specimen_evidence`, `conditions` and measurement `evidence`. A short `reason` belongs to the audit, not the scientific fact. Values, units, property names, entity identities, aliases, specimen declarations, group statuses and record order are protected. No new specimen, measurement, identity, numeric conversion or corrected value can be introduced by this route. An unresolved subject remains null rather than invented.

`context_review.apply_context_proposals(document, previous, proposals, review_focus=None, strict_focus=False)` is pure composition and makes no API call. It rejects malformed/out-of-range targets, duplicate edits, wrong anchors, unsupported existing specimens, foreign/unknown source selections and forbidden fields. Each valid proposed edit is tested against source/structural validation. If it introduces a new target-property validation reason relative to the base, the whole edit is held and the original context survives. An already-held fact may gain supported context while retaining its existing review reasons. Passing this guard is not a semantic guarantee; `applied_context_source_linked` means mechanical source linkage, not scientific certification. Immutable-field preservation and base/composed hashes are audited.

Optional `review_focus` is a strict list of `{entity_id, property_index, reason}`. It accepts only existing targets, recomputes their anchors and rejects extra structured answer fields. Reasons are explicitly **unverified source-audit hypotheses** to confirm or reject against the paper. They are source-audit feedback, so such a review is not a blind evaluation even when no checked values or desired answers are supplied.

With the backward-compatible default `strict_focus=False`, focus is navigation guidance. With **`strict_focus=True`**, only the listed original indexes/anchors are exposed as edit targets, and composition rejects even otherwise valid edits to unlisted properties. Their existing entity/specimen context and all original source chunks/catalog choices remain available. The strict source section is JSON data without a nested fresh-extraction instruction. Conditions must copy supported source phrases rather than expand an acronym or combine fragments into an unsupported value. A caller must pass the same focus and strict flag to the request and composition steps; a hint alone does not restrict application scope. Strict-only policy/audit fields are absent under the default, preserving earlier requests and audits.

Callers must preserve the base extraction, raw model proposals/trace, application audit and composed response as distinct artifacts. A composed response is derived model-reviewed data; it must not replace the raw fresh output or be labeled a fresh/blind test. Traces record the actual system/schema/user prompt hashes, prior-response hash and any source-audit-focus hash/strict flag. Historical source policies and code snapshots should remain reconstructible rather than rewriting prior receipts.

This scope also defines its limits: a missing structured thickness observation or wrong scientific value cannot be added or repaired by context-only edits. The selected Pei/Chen source review documents supported Pei observations alongside unresolved Chen measurement-context issues and a source-linked thickness note lacking a separate 12 μm observation. Those remaining issues are not erased by a successful Guo context edit. [Bounded source review](polymer-card-pei-chen-span-review-2026-11-06.md).

## Module interfaces

- `polymer_cards_lib.sources.load_documents(manifest_path)` returns a list of source documents. The manifest is `{papers:[{paper_id,title,domains,sources:[{path,format,source_part,expected_sha256?}]}]}`; paths resolve relative to the manifest. PDF, JATS XML and UTF-8 text retain meaningful location/chunk metadata. JSON source snapshots with `chunks` preserve manually selected original excerpts and their source locators; their coverage is explicitly selected excerpts, not a full-paper search. The loaded file's actual SHA256 is distinct from any declared original-document hash. Supplements belong to the same paper.
- `polymer_cards_lib.evidence_spans.build_span_catalog(document)` returns deterministic exact source choices; `resolve_span(document, chunk_id, span_id, catalog=...)` retrieves a selected range and its provenance without accepting model-written source text. `combine_adjacent_spans(document, resolved_refs, catalog=...)` adds only exact derived support from already selected overlapping/adjacent ranges within one chunk.
- `polymer_cards_lib.validation.build_cards(document, response)` implements the validation/output contract above.
- `polymer_cards_lib.prompt.build_system_prompt()` and `build_user_prompt(document)` provide the dedicated extraction instructions, including a clearly synthetic complete format example. Source-only `source_span_catalog`, `method_context_index` and `method_cross_reference_index` supply exact text choices, lexical protocol categories and same-Methods-section neighboring chunk IDs for explicit cues such as “same procedure” or “unless otherwise specified”. All original chunks remain supplied. These indices contain no checked answers or previous model proposals, are not exhaustive, and never assign a condition or specimen automatically. The model must trace healing conditions separately from subsequent tensile measurement and respect stated scope/exceptions. `build_response_format()` supplies the strict live schema; `extraction_profile()` supplies its provenance.
- `polymer_cards_lib.repair.build_revision_context(document, previous_response)` prepares untrusted proposals, validation feedback and exact-name source candidates without changing either input. `polymer_cards_lib.llm.revise_document(...)` submits one source-grounded revision request through the same bounded provider/error path as extraction.
- `polymer_cards_lib.context_review.build_context_review_prompt(...)`, `build_context_response_format()`, `context_property_anchor(...)` and `apply_context_proposals(...)` implement the bounded context contract above without network calls. `polymer_cards_lib.llm.review_context_document(...)` is the separate model-call wrapper. These are library APIs; the existing public CLI repair flags still request a full-record revision.
- `polymer_cards_lib.render.write_outputs(results, documents, out_dir, run_metadata)` writes `cards.json`, `cards.jsonl`, `cards.html`, `cards.md`, `audit.json` and `sources.json` without network requests. Every card fact's evidence is expandable/readable; HTML is escaped.
- Root CLI `extract_polymer_cards.py --papers MANIFEST --out-dir OUTPUT` uses the configured model. Default bounds remain three papers and 24,000 completion tokens per request. An explicit `--max-output-tokens` may request up to 48,000; a larger allowance does not make a truncated response acceptable. The actual request budget belongs in run metadata. `--request-timeout` defaults to 300 seconds per live request and accepts at most 900; SDK retries remain zero. `--records FILE` replays explicitly supplied `{responses:[...]}` without model calls. The two `--repair-*` flags instead make new model revision calls against matching prior source snapshots. Neither replay nor revision should be described as a fresh independent extraction.
